### 2. 主角角色 LoRA — 裁決：**不採納（Phase 3–4）；改造為 Phase 5+ 條件式備選**

- **可行性與 CU 成本評估（Colab／ComfyUI 影像側）**：
  - **閘道現況限制**：我方 `comfy-colab-kit` 閘道目前僅封裝推論 profile，**無現成 LoRA 訓練節點或 REST 端點**；若要訓練需另開獨立 Colab Notebook（`kohya_ss` 或 `ai-toolkit`）手動掛載 Drive 跑完，再把 `.safetensors` 權重回掛至 `sd-latest`／`flux-klein` 推論環境。
  - **CU 成本**：以 20–30 張圖訓練 Flux／SDXL 角色 LoRA（1,500–2,500 steps），在 **L4（~1.71 CU/hr）** 單輪約 45–90 分鐘（**1.3–2.6 CU**）；在 **A100** 單輪約 20–40 分鐘（**~2–5 CU**）。計入參數調優、防過擬合 3–4 輪驗證，實戰耗費約 **8–15 CU（佔 200 CU 月額 4%–7.5%）**——**算力花得起，真正的成本是 1–2 天工程調參工時與額外維護成本**。

- **為何相對現行 `gflow i2i` 參考鎖定，現在做 LoRA 屬於「負 ROI」**：
  1. **現行免費方案剛實證 100% 過關**：今日以 `fanli-master-B-userface.png` 單圖走 `gflow image i2i`（`nano2`），現代 4 張＋春秋布衣 2 張＋春秋朝服 2 張共 **8 張跨角度、跨年齡、跨朝代成品全數通過 QC**（僅 2 張重試 1 次，且主因為構圖／朝向提示詞而非變臉），成本 **0 Flow 點、0 Colab CU**。在參考鎖定尚未撞牆前投入 LoRA，直接違背 ADR-002。
  2. **引擎架構錯配（最關鍵盲點）**：圖像 LoRA **只能在 ComfyUI 的 `flux-klein`／`sd-latest` 產首幀時生效**——我方真正吃品質的 **Google Flow（Nano Banana 2／Veo 3.1）與 `minimax-h3-video`（Ref2V）完全無法載入自訓圖像 LoRA**。換言之，訓完 LoRA 無法提升影片段保臉率，只影響不走免費 Flow 產圖的少數首幀。
  3. **現有 master 圖量不足，硬訓必過擬合**：`casting/master/` 目前雖有 9 張本人臉成品，但含 1 張純背影、1 張 28 歲、1 張 60 歲、4 張古裝，且 **100% 是單一深灰棚光、半身平光構圖**。拿這套圖直接訓 LoRA，極高機率產生**「灰棚光過擬合」與「證件照僵硬表情」**——一進 `EP-001` 新創辦公室冷白螢幕夜戲或動態情緒鏡頭，反而比 `gflow i2i` 更容易穿幫。

- **肖像授權與資料治理規範（Creator 本人肖像原型專章）**：
  - **授權狀態**：此臉為 Creator 本人照片原型並親自核准，**肖像權與商用授權 100% 乾淨，不構成法律障礙**（且天然避開業界融臉侵權雷區）。
  - **強制資料管理規範（即便未來啟用 LoRA 亦須遵守）**：
    1. **三級隔離**：Creator 原始真實照片僅存個人私密空間，**不進入 VM 工作目錄**；產線僅使用衍生基準圖 `fanli-master-B-userface.png`；所有圖片、訓練集與 `.safetensors` 權重一律 `.gitignore` 排除，**永不進 Git repo**。
    2. **權重私密歸檔**：未來若訓練 LoRA，`.safetensors` 僅存私人加密 Google Drive `01_Bible/Models_Private/`，**嚴禁上傳 Civitai／Hugging Face 等公開站台**；Colab 訓練工作階段結束立即清除暫存碟。
    3. **雲端隱私查核**：送入 Google Flow 等外部服務前，由 Creator 確認帳號隱私設定關閉「內容用於模型訓練」（若提供該選項）。

- **未來啟用觸發條件（Phase 5+）**：須同時滿足「已累積 ≥25–30 張多光影、多表情、多景別之核准正片高分劇照（符合 `DESIGN.md` §2.1 原規則）」**且**出現「Flow 免費產圖收費／限流，被迫改由 ComfyUI `flux-klein`/`sd-latest` 承接大量主角首幀且參考鎖定過稿率 < 50%」時，始啟動訓練。

### 4. 低清預覽→升清（含「預覽階段同時驗口型」）— 裁決：**改造後採納**

- **對「預覽階段同時驗口型」的明確否決（技術現實）**：
  - 我方階段 3.5 預演使用的是 `wan-ltx-video`（LTX 低解析 `384×672` / `512×896`，$N=1$），該模型在 `DESIGN.md` §2.3 明確標記「無原生對白、保臉低、禁用於主角正臉」，根本無法產出有參考價值的精細口型。
  - 更根本的矛盾在於**跨引擎不可繼承**：階段 3.5 用 LTX 預演，階段 4 正式抽卡會切換至 **Veo 3.1 或 MiniMax H3 Ref2V**——換引擎重算後嘴部動作 100% 重置，預演段驗口型既驗不準、結果也帶不到正片。
- **改造後的正確做法（「兩層分責」＋「Colab 同引擎降清挑片→升頻備案」）**：
  1. **階段 3.5（LTX 預演，常線，~0.5 CU/集）維持原職責並加一項零成本動作**：只驗**全集節奏、景別切換、TTS 正式對白語速／發音與停留秒數**（明文寫死**不驗口型**）；同時在預演階段標記所有正臉特寫開口鏡（`LIP_SENSITIVE`），凡單句過長者當場改拆為「開口 2 秒＋切合約／白板／反應鏡＋回切收尾」，從剪輯結構根治口型風險。
  2. **把輸入的「低清挑完再升清」改造落地於階段 4 的 Colab H3 鏡頭**：若 EP-001 實測（§5.3(c)）發現 H3 跑目標檔 `768×1344` 在 L4 上單次耗時超標（>8–10 分鐘）或 OOM，則對常規中景 H3 鏡改採**「同引擎兩段式」**：先以 H3 降載檔 **`544×960`（~0.52 MP）** 跑 $N=3$ 抽卡、由挑片頁同步掛載 `audio_tts/*.wav` 選出**口型節奏與表演最自然的那 1 支** → 再僅對該支入選片段做高清放大（Phase 3/4 先採 `ffmpeg` Lanczos；Phase 5 視需求加掛輕量影片超分模型），實質省下 30%–45% Colab CU，且**不會因為換模型重算而丟失挑中的口型**。
  3. **Phase 5 口型進階備案**：若 EP-001 實測 §5.3(b) 發現「TTS 先行＋影片 prompt 帶台詞提示＋景別調度」在少數近景特寫仍低於 3.8/5.0 分，再於 Phase 5 針對每集 2–3 顆正面特寫評估 Colab 開源音訊驅動口型（Wan 2.2 語音驅動或 LatentSync）。

### 拍板 1：EP-001 是否正式依 ADR-002 改採「Phase 3 半自動先跑通，8 支系統腳本延至 Phase 5」？

- **選項 B**：維持 `DESIGN.md` v1.3 原案，先花 3–5 天寫齊 8 支 P0 腳本，再開拍 EP-001。

### 拍板 2：MiniMax H3 開源權重於 Colab 執行的「美區機房地域限制」合規方針

- **選項 B**：認定創作者與目標受眾均在台灣（非美歐英韓），維持原計畫於 Colab 執行 `minimax-h3-video` 開源權重，暫接受雲端算力節點位於美區之條款灰區。

### 拍板 3：是否鎖定「減法紀律」（不導入 Toonflow／LocalMiniDrama、不開 Kling 訂閱、不預訓 LoRA），全力補齊 EP-001 最小資產銀行並開拍？
